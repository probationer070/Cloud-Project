# P4 Design — AI Chatbot (Customer-Service AI Chatbot)

**Directory:** `project4-ai-chatbot/`
**Stack:** API Gateway (HTTP v2) + Lambda + DynamoDB + SSM + SNS + S3 + CloudFront + CloudWatch
**Region:** `ap-northeast-2` (Seoul)

## Purpose

A Gemini-API-based customer-service chatbot. It receives messages on a REST API endpoint,
keeps conversation history in DynamoDB, and returns AI responses. When an agent handoff is
needed it sends an email notification via SNS, and the web UI is served from S3 + CloudFront.

> **Project independence:** P4 does not reference the deployed infrastructure of P1/P2/P3. It
> creates every AWS resource it needs (S3, CloudFront, DynamoDB, SNS, API Gateway) with its own
> Terraform, so it can be deployed and tested on its own without P1–P3.

## Architecture

```
Browser / curl
    → CloudFront (HTTPS) ─ OAC ─▶ S3 (web UI, private)
    → API Gateway HTTP v2 (POST /chat)
         ▼
    Lambda chatbot (ARM64, 256MB, timeout 45s)
    ┌────────────────────────────────────────────────────┐
    │ 1. get_history   DynamoDB Query (last 10 turns)    │
    │ 2. build_prompt  assemble System Prompt + history  │
    │ 3. call_ai       Gemini API (HTTP 25s)             │
    │                  or Bedrock InvokeModel            │
    │ 4. route         ESCALATE / profanity / fallback   │
    │ 5. save_history  DynamoDB BatchWriter              │
    └────────────────────────────────────────────────────┘
         │                     │
    DynamoDB               SSM Parameter Store
    (sessions, TTL 24h)    (Gemini key, fetched once at cold start)
         │
         ▼ (on ESCALATE detected)
       SNS → email

CloudWatch alarms (error count > 5, response time > 10s) → SNS → email
```

## Lambda 5-Step Flow

| Step | Function | Action |
|------|------|------|
| 1 | `get_history` | DynamoDB Query — fetch the last 10 turns by `session_id` |
| 2 | `build_prompt` | assemble System Prompt + conversation history + current message |
| 3 | `call_gemini` / `call_bedrock` | call the AI API (HTTP timeout 25s / Bedrock boto3) |
| 4 | `route_response` | detect `ESCALATE` keyword → publish to SNS; detect profanity → warning response; timeout → fallback |
| 5 | `save_history` | DynamoDB BatchWriter — store user/assistant messages, TTL = now + 24h |

## DynamoDB Conversation-History Design

Key design and timestamp rules for the DynamoDB table `p4-chatbot-sessions`.

### Key Structure

| Attribute | Type | Role |
|------|------|------|
| `session_id` | S (PK) | Session identifier. Generated by the frontend (`"web-" + random()`) |
| `timestamp` | S (SK) | ISO 8601 + ordering suffix. Ascending sort guarantees conversation order |
| `role` | S | `"user"` or `"assistant"` |
| `content` | S | Message body |
| `ttl` | N | Unix epoch. DynamoDB TTL auto-deletes after 24h |

### Timestamp Suffix Rule — `_0` (user) / `_1` (assistant)

`save_history()` stores one turn (user + assistant) at the same ISO timestamp, distinguished by a suffix:

```
2026-06-05T14:23:45.123456+00:00_0   →  role: "user"
2026-06-05T14:23:45.123456+00:00_1   →  role: "assistant"
```

**Why `_0` / `_1`?**

DynamoDB sorts the SK in ascending string order. When two messages share the same ISO
timestamp, `'0' < '1'`, so the user message always comes before the assistant message.

The previous implementation used `_user` / `_assistant`; since `'a' < 'u'`, the assistant
sorted before the user. The pairing loop in `get_history()` assumes `[user, assistant]` order,
so items read in the wrong order all failed to pair and conversation history was lost. In
conversations of 3+ turns, the previous turn's user message cross-matched with the next turn's
assistant message, feeding the wrong context to the AI — the repeated-response bug
(see changelog `26-06-05`).

### get_history() Pairing Logic

```python
# ScanIndexForward=True → SK ascending = [user_T1, asst_T1, user_T2, asst_T2, ...]
items = table.query(KeyConditionExpression=Key("session_id").eq(session_id),
                    ScanIndexForward=True, Limit=MAX_HISTORY_TURNS * 2)
# pair into [user, assistant]
while i + 1 < len(items):
    if items[i]["role"] == "user" and items[i+1]["role"] == "assistant":
        history.append({"user": items[i]["content"], "assistant": items[i+1]["content"]})
        i += 2
    else:
        i += 1  # skip malformed item
```

The `_0` < `_1` suffix is a precondition of this logic. If you change the suffix, you must preserve this ordering invariant.

## Security Notes

- The Gemini API key is not an environment variable — SSM SecureString (KMS-encrypted), fetched once at cold start, then cached in the container.
- The Lambda IAM role is least-privilege: allowed only on the specific DynamoDB table, SNS topic, and SSM parameter ARNs.
- The Lambda CORS response header is pinned via the `ALLOWED_ORIGIN` environment variable to the CloudFront origin (no wildcard `*`).
- API Gateway CORS is set to `allow_origins = ["*"]` — restrict it to the CloudFront domain in production.
- `force_destroy = true` is a dev convenience — remove it in production.

## AI Provider Switching

Change the `ai_provider` and `gemini_model` values in `variables.tf`, then run `terraform apply`:

```hcl
ai_provider  = "gemini"            # default
gemini_model = "gemma-4-26b-a4b-it" # current model: Gemma 4 26B (free, 1,500 req/day)
# gemini_model = "gemini-2.0-flash" # older model (no daily cap; per-minute request-rate limits apply)

ai_provider = "bedrock"            # Claude 3 Haiku (requires a payment card, us-east-1)
```

You can switch between Gemini-family models with only the `GEMINI_MODEL` environment variable,
no code change. Gemma models use the same `call_gemini()` function and `v1beta` endpoint.

## Deployment Sequence

For the full deployment procedure, see [`README.md`](../../project4-ai-chatbot/README.md).

Summary:
1. Issue a Gemini API key (Google AI Studio)
2. Edit `variables.tf` (suffix, alert_email)
3. `terraform init && terraform apply` (creates the SSM parameter as a placeholder)
4. Seed the real key once: `aws ssm put-parameter --name /cloud-portfolio/gemini-api-key --value ... --type SecureString --overwrite`
5. Enter `chat_api_endpoint` in `website/index.html`
6. `aws s3 sync` + CloudFront cache invalidation
7. Open in a browser and test with curl
